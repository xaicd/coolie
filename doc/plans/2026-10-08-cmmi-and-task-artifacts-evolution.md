# 任务与 CMMI 产物质量根本变革：从“伪文档虚假空转”走向“Spec-First 可执行活体交付物”

> **作者**：Coolie 平台特派 FDE 审计组  
> **审视背景**：老板 2026-10-08 深刻警醒——「我们的任务、CMMI 过程都没有有效高质量的产物出现，还不如 spec 驱动的结果呢」。  
> **核心使命**：彻底砸碎 CMMI 的纸面官僚主义与模板废话，吸取 Spec 驱动的“凝练、精准、可断言”，将任务流转与 G1-G5 门禁重构为**以“真实物理交付物 (Executable Artifacts)”为唯一硬门槛的活体交付引擎**。

---

## 一、 根因解剖：为什么现有的任务与 CMMI 产物惨败给 Spec 驱动？

老板的一句话，彻底撕开了大模型时代软件工程“伪文档生成”的遮羞布。我们必须直面三大血淋淋的根因：

### 1. 形式主义模板逼出了“AI 套话垃圾” (Paperwork Delusion)
* **现状**：传统 CMMI 要求“软件需求规格说明书 (SRS)”、“概要设计 (HLD)”、“详细设计 (LLD)”。当数字员工领到这些任务时，最容易的做法就是让 LLM 生成一套长达数十页的模板套话（系统概述、行业背景、非功能性需求、可维护性原则……）。
* **后果**：
  - **没人读**：无论是老板、交付客户还是后续接手的数字员工，没有人会去读这几万字的 AI 废话；
  - **不能运行**：文档里全是抽象名词，没有一个结构化 Schema，没有一条可断言的测试用例；
  - **严重脱节**：文档写归写，代码写归写，两张皮空转。

### 2. 反观：为什么 Spec 驱动能出高质量结果？
* **极度凝炼**：Spec 驱动只认三步（Requirement → Design → Task），严禁任何客套话；
* **可断言与机器可读**：每一条需求都必须用 EARS 规范表达（`WHEN...THEN...SHALL`），可以直接转译为自动化测试断言；
* **代码与实体强绑定**：Design 部分直接精确到“改哪几个文件、哪个接口、加哪个字段”，产物直接就是**通过编译的代码与单元测试**，自然扎实、有效、高质量。

### 3. 任务（Task）结项的“无交付物漏洞” (The No-Deliverable Flaw)
* **致命缺陷**：系统内很多任务只要状态被置为 `done` 就结项了，根本不强制要求挂载任何 Deliverable；
* **对比亮点**：昨天我们在真机实测中看到的九夏智居 `[开发] 板材算料开料优化算法`，之所以惊艳，是因为它挂载了 `📎 数控开料排版优化算法与钻孔规范`（含有 76.42% 欧松板利用率、32mm 系统孔坐标与 30 件板件数控清单），在沙箱里**一键就能渲染、直接能拿去指导生产**。但整个系统中，像这样拥有硬核交付物的任务少之又少！

---

## 二、 核心变革原则：Doc as Code & Spec-First CMMI

我们绝不要传统软件外包那套自欺欺人的“文档堆叠”，必须全面推行三大军规：

### 军规一：全面废黜“伪长文生成”，产物只有五种合法形态
凡是不能直接指导运行、不能作为断言依据、不能在沙箱中渲染的文字，统统判定为**垃圾废产物**。系统只认可五种高保真交付物：
1. **可交互沙箱原型 (Interactive Sandbox Prototype)**：
   - HTML / 3D 原型 / 真实移动端 React Native 组件包，能在手机端沙箱中实时点开操作；
2. **业务数据与加工成果 (Operational & Engineering Output)**：
   - 如开料排版 DXF、BOM 物料清单 Excel、数控加工 G 代码、企微触达策略 JSON 配置；
3. **精准 Spec 契约集 (Executable Spec Contracts)**：
   - 严格遵循 Kiro / EARS 规范的三段式契约，单篇不超过 100 行，直接作为测试脚本的输入源；
4. **商业与真实度量凭证 (Business Metrics & Ground Truth Evidence)**：
   - 真实利用率计算表（如 ≥75%）、成本核算对比表、Android 模拟器 1080P 拟真人全态截图；
5. **严密的代码与测试脚本 (Validated Code & Automated E2E)**：
   - 经过 0 编译报错拦截的 Git Commit、包含输入输出断言的测试脚本。

### 军规二：任务流转推行“无物理交付物严禁结项 (No Artifact, No Done)”
* **物理拦截**：修改任务状态机，任何数字员工（铁匠、门神、墨斗）在调用 API 将任务从 `in_progress` 置为 `done` 时，后端服务强制执行门禁：必须挂载至少一项通过校验的真实交付物，否则直接 422 阻断，杜绝“口头交工”。

### 军规三：将 CMMI 阶段全面“Spec 化、实体化、度量化”
彻底摒弃传统 CMMI 繁文缛节，吸纳 Spec-driven 的精华，重新定义 G1-G5 的唯一交付物标准：
- **G1 需求**：结构化 EARS 需求 Spec (`WHEN...THEN...SHALL`) + 业务对象 (Object) 状态转移矩阵；
- **G2 架构**：活体本体 Schema 定义 (ObjectTypes + ActionTypes) + 模块单向依赖图；
- **G3 实现**：编译 0 报错的代码 Commit + 可在移动端沙箱直接预览的高保真交互原型；
- **G4 验收**：关键商业指标计算书（如板材利用率 76.42%）+ 宿主机真机 1080P 全态快照证据；
- **G5 投产**：不可变生产环境部署指纹 (SHA256) + 真实客户会签单/验收回执。

## 三、 明日审查落地实施路径（破局三步走）

1. **第一步：打补丁（任务完成硬门禁）**
   - 在 `server/src/services/issues.ts` 中加入 `No Artifact, No Done` 校验，切断数字员工“口头完工、交差了事”的退路；
2. **第二步：清理历史死文档，将 CMMI 模板全面降维为 Spec 契约**
   - 把 `docs-coolie/cmmi/` 下那些套话 Markdown 模板彻底删除或重写，全面替换为轻量级、机器可读的 EARS Spec 骨架；
3. **第三步：升级产物交付中心（Artifacts Center）体验**
   - 强化移动端和 Web 端产物中心的“即刻体验沙箱”与“指标高亮卡片”，让客户和老板点进任务第一眼看到的就是**能跑的原型、扎实的数据、真实的收益**，而不是空洞的报告。
