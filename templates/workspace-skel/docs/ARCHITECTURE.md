# ARCHITECTURE —— Coolie 开发基座

> 本文件属于每个新建公司的 workspace。它是**基座**的架构说明：基座提供什么、
> 边界在哪、客户标书落地时从哪扩展。

## 1. 设计原则

1. **基座不含业务。** 业务（订单 / 审批流 / 商城 / CRM / ERP / WMS / MES / IM …）
   一律不预装；需要哪个就在该项目的 workspace 里引入或实现哪个。
2. **默认模块只放「每个项目都要」的底座能力。** 组织与访问、基础设施、会员、
   审计、对外契约 —— 少一个都活不了，且都不含业务语义。
3. **按标书快速定制。** 目标是「拿到标书/需求文档 → 立刻在基座上开发」，
   而不是「先花几天删掉用不上的域」。
4. **不动主仓。** 基座骨架由主仓 `templates/workspace-skel/` 定义；
   具体项目只在本 workspace 内生长，不回写主仓。

## 2. 分层

```
┌──────────────────────────────────────────────┐
│ 业务定制层（按标书新增，基座不含）            │
│   订单 / 审批流 / 报表 / 商城 / CRM / ERP …   │
├──────────────────────────────────────────────┤
│ 默认模块层（基座自带 5 个）                   │
│   system  infra  member  audit  api          │
├──────────────────────────────────────────────┤
│ 底座代码（可选, 轻量 tag coolie-base-1.0）    │
│   认证 / 权限 / 存储 / 代码生成 / 通知 / 任务 │
└──────────────────────────────────────────────┘
```

- **底座代码**由 `scripts/new-company.sh` 按需拉取（`coolie-base-1.0` tag），
  仍然**不含业务域**；拉不到不影响立项，可先只用骨架。
- **默认模块层**是本目录 `../modules/` 的 5 个模块，定义边界与扩展点。
- **业务定制层**是本项目真正花钱的地方，标书写到哪做到哪。

## 3. 5 默认模块 vs 15 全栈域

旧的「全栈 15 域」底座（`ruoyi-all-next` 全量）把 10 个业务域也一起预装了。
本基座只保留 5 个默认模块。

| 维度 | 5 默认模块（本基座） | 15 全栈域（旧底座） |
|---|---|---|
| 自带模块 | system / infra / member / audit / api | 上述 5 个 + bpm / pay / report / mp / mall / crm / erp / wms / mes / im |
| 业务语义 | **无**（真·空壳） | 强（一堆用不上的表与菜单） |
| 首次启动 | 快（模块少、依赖少） | 慢（全量编译 / 迁移 / 塞满的菜单树） |
| 交付节奏 | 拿到标书即可定制 | 先删域，再开发 |
| 需求不符时 | 直接加 | 要改别人的业务实现 |
| 适用 | **任何项目**（按标书定制） | 只有刚好命中那 10 个域的项目 |

**为什么这样选：** 一个交付项目命中全部 15 域的概率极低；预装的 80% 是负担 ——
它占用启动时间、迁移时间、菜单空间，还在「需求与预装实现不一致」时变成改造负担。
基座保持空壳，业务按标书快速定制，是净收益。

## 4. 按标书定制开发（playbook）

1. **读标书 → 落 spec。** 把标书/需求文档放 `../specs/`，走仓库的 spec workflow
   （需求 → 设计 → 任务），产出可追踪的需求条目。
2. **定领域与边界。** 用 FDA 角色 skill 画死隔离 / 领域 / 权限 / 守恒边界；
   明确哪些落在 5 个默认模块内，哪些新建模块。
3. **默认模块直接用，不重造。** 认证、权限、存储、代码生成、通知、定时任务来自
   基座；业务模块站在它们之上。
4. **业务模块按需引入。** 标书要的域（审批流 / 商城 / …）在本 workspace 内实现，
   可复用成熟开源实现；**不要求**与主仓或其他项目一致。
5. **门禁收口。** 按 CMMI 门禁（G1 需求 → G2 架构 → G3 编译 → G4 验收 → G5 投产）
   逐关收口，角色见 `../cli/`、`../models.yaml`。
6. **交付物留痕。** 交付产物、审计、验收记录按项目约定归档。

## 5. 扩展点

| 想加什么 | 加在哪 |
|---|---|
| 新业务域（订单 / 审批 / 商城…） | `../modules/<new-domain>/` 新建模块，自带 README |
| 底座能力（认证 / 存储 / 生成…） | 优先用默认模块；确需扩展时改 `infra` / `system` |
| 角色与派单 | `../cli/<role>.sh`（骨架，按项目补实现）；`../models.yaml` 设 CLI/模型 |
| 文档 | `../docs/`（设计/运维）、`../specs/`（需求） |

> 骨架说明：基座里的 `cli/*.sh` 是**空函数 + TODO** 的骨架，不含业务逻辑；
> 落地时按本项目实际派单方式补全（见各脚本内 TODO）。
