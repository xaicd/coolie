# Agent-Device & Agent-Browser 自动化验证与运营最高工程法典

> **法典标识**: `RULE_VERIFICATION_AUTOMATION`
> **生效范围**: 全体数字员工 (Hermes / 墨斗 / 铁匠 / 门神 / 兑底渊 / 百晓生) 及自动化执行引擎
> **核心工具**: `agent-device` (移动端模拟器/真机驱动) · `agent-browser` (Web 浏览器驱动)
> **权威地位**: 平台最高宪法级守卫，违反本法典任何一条，门禁直接阻断并判定为假交付。

---

## 第一条：真实环境物理直连与宿主穿透铁律 (Physical Environment Grounding)

1. **真实硬件与模拟器绑定**：
   - 移动端原生自动化验证必须物理连接真实的 Android 模拟器 (AVD / Pixel) 或真机，严禁使用浏览器模拟 UA (Emulated User-Agent) 冒充移动原生端；
   - 运行于 Linux 容器环境的数字员工，必须统一通过 `host-exec "agent-device <args>"` 穿透至 Mac Studio 宿主机执行，严禁在无图形环境的容器内尝试裸启动原生模拟器。
2. **Web 真实网络与上下文对齐**：
   - `agent-browser` 自动化必须直连真实的 Web 服务端口（本地开发环境 `http://localhost:3100` 或生产环境域名），严禁仅对静态 HTML 字符串进行脱机正则匹配；
   - 必须真实拉取 API 数据、解析并挂载 Pinia/Redux 状态机。

---

## 第二条：状态机四态穷举与假死按钮零容忍铁律 (Four-State Machine & Zero-Dead-End)

1. **四态穷举覆盖率 100%**：
   - 任何交付验收的页面或表单，必须穷举四态：
     - **空态 (Empty)**：无数据时必须展示友好中文占位图与引导操作；
     - **加载态 (Loading)**：接口延迟 > 100ms 必须有骨架屏或禁用按钮展示，防止重复点击；
     - **成功态 (Success)**：数据落地后必须有轻量非侵入 Toast 或就地局部数据刷新；
     - **异常态 (Error)**：网络异常或 4xx/5xx 必须提供明确中文原因与【重试】两字按钮。
2. **假死按钮立即亮红牌**：
   - 页面中所有可点击元素（Button、Link、Icon）必须产生确定性的行为流转；
   - 凡发现点击后没有任何网络请求、状态变更、弹窗弹出或 Toast 提示的“死穴假按钮”，一律判定为 **Critical 缺陷**，当即阻断 G4 验收。

---

## 第三条：物理几何遮挡审查铁律 (Physical Occlusion & Geometry Guard)

1. **真实触碰面判定标准**：
   - 严禁单纯使用 `element.isVisible()` 作为可交互判定依据；
   - 必须通过物理坐标几何计算：`document.elementFromPoint(centerX, centerY)` 验证位于顶层可交互的正是目标元素本身；
   - 凡发现提交按钮被悬浮窗、半透明蒙层、全屏透明遮罩拦截点击，或者被 Fixed 底栏盖住者，一律判定为 **Blocker 阻断性缺陷**。
2. **软键盘弹出与视口避让**：
   - 移动端表单在呼出系统软键盘后，输入框与确认提交按钮必须自适应滚动暴露在软键盘上方，严禁键盘挡住输入焦点或操作键。

---

## 第四条：不可篡改真机多模态存证铁律 (No Artifact, No Done)

1. **法定机器证据三件套**：
   - 每次自动化测试、G4/G5 门禁走查或长效巡检结束，必须在工作区留下可验证的三件套：
     1. **结构化运行报告** (`evidence/automation-run-report.json`)：记录每个用例的耗时、网络请求数、断言结果；
     2. **多模态真实屏幕快照** (`evidence/screenshots/*.png`)：记录关键业务步骤的高清真机截屏；
     3. **控制面工件登记** (`issue_work_products`)：通过 API 将产物登记至工件总线。
2. **绝对造假一票否决**：
   - 严禁通过人工伪造通过、编写空断言 `expect(true).toBe(true)` 或跳过错误步骤；
   - 门禁脚本必须校验快照文件的物理修改时间戳与 SHA-256 校验和。

---

## 第五条：双轨生命周期严格隔离铁律 (Testing vs Operations Dual-Track)

1. **测试验收阶段 (Stage 1: Testing & Verification)**：
   - 专属于软件交付过程中的 G4 全栈验收与 G5 投产发布；
   - 重点关注代码实现是否符合 SRS 需求规格与 HLD 架构设计，验证通过后方可合流发版。
2. **长效运营阶段 (Stage 2: Operations Patrol)**：
   - 专属于商业软件发布后的线上常态化巡检与稳定性维护；
   - 每日定时执行 SLO 核心旅程探活、孤立实体扫描、门禁越界清查、版本一致性核对；
   - 运营发现异常自动生成缺陷工单与 5-Whys 根本原因分析记录。
