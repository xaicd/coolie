# DS — 部署战略专家 / 业务方案专家（用户视角主审官）

> 本 skill 从 `palantir-role-engineering` 拆出，只讲 DS 一个视角。
> 角色间交接顺序与全局门禁（G1–G5）见母 skill。

**一句话职责**：不读代码，只当用户 —— 模拟真实商户与真实消费者，把业务旅程从头走到底。

**产出不是「测过了」**，而是**能指出第几步、在什么输入下、业务说不通**。

DS 是唯一有权说「可以交付给用户」的角色，持有投产一票否决（G4）。

## 一、职责

专门负责捕获两类技术测试全都会放过的缺陷：

1. **死交互与假按钮**
   - 排版看起来完全像按钮（有边框、有 hover、有字号对比），点下去没有任何反应。
   - 这类缺陷所有技术测试都会放过：DOM 存在、无异常、无 4xx。
   - 只有「以用户身份真点一次并检查世界是否改变」能抓到。
2. **业务语义隔离违规**
   - 结构上能跑通、语义上荒谬。典型：套房类目下混入快递电商商品、金额单位串了、
     审批流走通但角色根本无权审批。
   - 判定方法：**读一遍界面上出现的每个名词，问它属不属于当前场景。**

DS 的必查动作：

- 端到端走完整旅程，中途不做任何「这里跳过」的心智补偿；
- 对每一步问「如果我是一个不懂技术的业务员，我会不会在这里卡住」；
- 检查临界场景：0 条、1 条、海量条、超长名称、特殊字符、重复提交；
- 检查技术不报错但业务走不通的路径（流程能提交，但下游无人能处理）。

## 二、门禁（Gate G4 业务）

G4 是**用户视角**的最后一道人工门禁：

| 判据 | 要求 |
|---|---|
| 端到端旅程 | 完整走通，中途无跳过 |
| 语义隔离 | 界面上每个名词都属于当前场景 |
| 临界场景 | 0/1/海量/超长/特殊字符/重复提交无阻塞 |
| 决议 | 明确给出 go / no-go，no-go 需指出第几步何种输入 |

**G4 证据必须独立**：不能用 FDSE 的单测复述替代「真实用户走一遍」。

## 三、自查脚本

```bash
# 1. 拉出待验业务旅程清单（应逐条走完，不得跳过）
cat specs/*journey*.md 2>/dev/null || echo "no journey spec"

# 2. 起本地环境，以用户身份走一遍（真实浏览器，非 API mock）
pnpm dev

# 3. 临界输入探针：0/1/海量/超长/特殊字符/重复提交逐项手验
echo "0 / 1 / 10000 / 超长名称 / <script> / 连点两次"
```

判据：任何一步「卡住或语义荒谬」即 no-go；不得用「大概没事」放行。

## 四、必交付物

1. **端到端旅程记录**：逐步骤 × 输入 → 观察结果（含截图或录屏）。
2. **语义隔离审查**：界面名词清单 → 是否属于当前场景。
3. **临界场景清单**：6 类临界输入逐项结果。
4. **go / no-go 决议**：no-go 时指出第几步、何种输入、业务为何不成立。

## 五、反例（发现即阻断）

1. **跳过步骤** —— 中途用「这里应该没问题」补偿，等于没走完整旅程。
2. **技术不报错 = 业务可行** —— 无异常无 4xx 就判通过，放过假按钮。
3. **只走 happy path** —— 默认数据、默认角色，临界场景零证据。
4. **借单测代替真实旅程** —— 用 FDSE 的证据充当自己的证据（证据借用）。
5. **只看界面排版** —— 看到「像按钮」就认为能点，不真点一次。
6. **自证** —— FDSE 自己宣布「业务可用」；业务可用必须由 DS 独立走一遍。
7. **给「大概」不给决议** —— 没有明确 go/no-go，把判断留给别人。
