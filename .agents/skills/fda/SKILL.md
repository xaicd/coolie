# FDA — 前线架构师（Forward Deployed Architect）

> 本 skill 从 `palantir-role-engineering` 拆出，只讲 FDA 一个视角。
> 角色间交接顺序与全局门禁（G1–G5）见母 skill。

**一句话职责**：在任何人写第一行代码之前，把不可逾越的边界画出来，
并指出边界在哪个文件、哪一层被强制。

**约束方向**：FDA 的约束在实现**之前**生效，是设计约束，不是建议。

## 一、职责

1. **组织与租户数据隔离**
   - 每个实体归属哪个租户，隔离落在路由层 / 服务层 / 数据库层哪一层。
   - 隔离必须在**服务端**强制；客户端传来的租户标识永远不可信。
   - 跨租户访问的拒绝路径要可枚举（403 还是 404，取决于是否泄露资源存在性）。
2. **领域模型边界**
   - 哪些概念属于哪个域，什么不允许混在一起。
   - 领域边界一旦模糊，后续所有功能都会长出跨域的特例分支。
3. **RBAC 权限边界**
   - 谁能读、谁能写、谁能批，逐操作列出。
   - **能提案 ≠ 能批准**；自批自审的流程等于没有流程。
4. **不可篡改事务边界与守恒**
   - 资金、库存、配额类操作必须有原子事务边界（含失败回滚）。
   - 守恒断言：进出双向对账、防重复冲销。守恒破坏通常是静默的，必须主动断言，
     不能事后抽查。

## 二、门禁（Gate G1 设计）

过 G1 必须能**现场指出**（不是口头承诺）：

| 检查项 | 必须能回答 |
|---|---|
| 租户隔离点 | 隔离在哪个文件 / 哪一层强制？绕过路径在哪被拒？ |
| 领域边界 | 新增实体属于哪个域？越域访问如何被拦？ |
| 权限矩阵 | 读 / 写 / 批分别谁有权限？提案与批准是否分离？ |
| 守恒断言 | 断言写在哪个事务里？重复提交如何防？ |

**任一条答不上 → 不得进入 Core SWE / FDSE 实现阶段。**
隔离、权限、守恒任一条被绕过，交付物整体不予验收。

## 三、自查脚本

交付前运行（命令为辅助，G1 最终判据是能指出强制点）：

```bash
# 1. 列出所有查询，确认每个都带 company/tenant 约束
grep -rn "findMany\|findFirst\|\.select(" server/src --include="*.ts" \
  | grep -v "companyId\|tenantId" | head -20

# 2. 列出所有写接口，确认存在权限校验
grep -rn "router\.\(post\|patch\|put\|delete\)" server/src/routes --include="*.ts" | head -20

# 3. 列出资金/库存类写操作，确认被事务包裹
grep -rn "\.transaction(\|BEGIN" server/src --include="*.ts" | head -20
```

判据：第 1 条出现无租户约束的查询即红；第 2 条出现无权限校验的写接口即红；
第 3 条出现无事务包裹的守恒写操作即红。

## 四、必交付物

1. **隔离设计片段**：文件路径 + 行号级的隔离强制点清单。
2. **领域边界图**：新增/改动实体归属哪个域，越域路径如何被拒。
3. **权限矩阵表**：操作 × 角色，读/写/批三列，标注提案与批准是否同人。
4. **守恒断言清单**：每个资金/库存操作对应的断言与所在事务。

## 五、反例（发现即阻断）

1. **客户端传租户 ID 当权威** —— 请求体里的 `companyId` 直接当过滤条件，
   改一个字段就能读别家数据。
2. **约定式隔离** ——「所有查询记得加 companyId」，靠人记，必然漏。
3. **自批自审** —— 同一角色既能创建又能批准，审批流形同虚设。
4. **守恒靠事后抽查** —— 不对账、不防重，等月末发现数字对不上。
5. **边界模糊换灵活** —— 两个域的表混用一张宽表，后续每个功能都要处理特例。
6. **隔离在客户端** —— 只在 UI 藏按钮，接口裸奔。
