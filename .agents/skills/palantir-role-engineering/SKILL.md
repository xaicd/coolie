# Palantir Foundry 角色工程工作流

本技能把一份交付物拆成五个角色视角，每个视角有**自己的文件面、自己的门禁、自己的证据要求**。
角色不是为了分工好看：每个角色都对应一类**只有从这个视角才能看见的失败**。一个角色缺席，
就意味着它那一类失败会一路走到用户面前。

**核心原则：证据不可跨角色借用。** FDSE 的单测全绿不能顶替 DS 的业务探路；
Core SWE 的编译通过不能顶替 PRE 的环境一致性；任何角色的自述都不能顶替可复现的证据。

## 1. 角色拓扑与约束方向

```
                  ┌────────────────────────────────────────────────┐
                  │     FDA (Forward Deployed Architect 前线架构师)  │
                  │     组织与租户数据隔离 / 领域模型 / RBAC 权限边界   │
                  └───────────────────────┬────────────────────────┘
                                          │ 指导与约束（先于实现）
                                          ▼
     ┌────────────────────────────────┐   ┌────────────────────────────────┐
     │  Core SWE (平台核心研发工程师)   │   │  PRE (产品可靠性工程师 / SRE)    │
     │  编译器拦截 / 静态 AST 门禁      │   │  环境对齐 / 不可变制品指纹       │
     │  增量 typecheck 0 报错拦截       │   │  发布后健康拨测 / 灰度验证       │
     └───────────────┬────────────────┘   └───────────────┬────────────────┘
                     │ 基础设施支撑                        │ 运行环境护航
                     ▼                                     ▼
     ┌───────────────────────────────────────────────────────────────────────┐
     │              FDSE (Forward Deployed Software Engineer 前线部署全栈)    │
     │              【交付第一责任人】全栈功能开发 / 防御性 UI / 状态机全覆盖    │
     │              亲自编写自动化 E2E 与单测 / 杜绝死穴按钮与未捕获异常         │
     └───────────────────────────────────┬───────────────────────────────────┘
                                         │ 交付物提交 UAT 冒烟
                                         ▼
     ┌───────────────────────────────────────────────────────────────────────┐
     │              DS (Deployment Strategist 部署战略专家 / 业务方案专家)     │
     │              【用户视角主审官】业务旅程真实探路 / 临界场景穿透            │
     │              验证商业闭环与用户体感，杜绝“技术不报错但业务走不通”          │
     └───────────────────────────────────────────────────────────────────────┘
```

**约束是单向的**：FDA 的约束在实现之前生效；Core SWE 与 PRE 的支撑在实现之中生效；
FDSE 的交付在 DS 之前；DS 是唯一有权说“可以交付给用户”的角色。
反向不成立 —— FDSE 不能自己宣布业务可用，Core SWE 不能替 FDA 决定租户边界。

## 2. 角色职责矩阵

### 2.1 FDSE — 前线部署全栈工程师（交付第一责任人）

**对写下的每一行前后端代码负终身可用性责任。** 不是“提交完就算交付”。

必须做到：

1. **状态机穷举** —— 严禁只测默认 Tab、默认筛选、默认分页。一个界面有 N 个状态分支，
   就要有 N 条路径的证据；空态、错误态、加载态、超长文本、权限不足态都算状态。
2. **零死穴原则** —— 每个看起来是按钮的东西必须有真实业务回调。禁止渲染了
   `onClick` 却只 `console.log`、`toast('开发中')`、或者干脆没有 handler 的“假按钮”。
   做法上：**按钮出现即代表动作存在**，动作不存在就不渲染按钮（渲染禁用态并说明原因也可以，
   但不可以假装可点）。
3. **异常防御** —— 前端不得出现未捕获异常；后端不得把内部错误原文抛给界面。
   每一个 `await` 的失败路径都要有明确去向（提示、降级、重试），不允许静默失败。
4. **自己写测试** —— 自己写单测与 E2E，不外包给“测试角色”。理由：写测试的人不知道
   边界在哪，就会写出只覆盖 happy path 的测试。

**反面清单（本章节最常抓到的四类）**：
- 只测默认 Tab，切到第二个 Tab 就白屏；
- 按钮点了没反应（`onClick` 缺失或指向未定义函数）；
- 列表在空数据时渲染出无意义的 `undefined` / `NaN` / 假 ID；
- 改了后端字段名，界面继续读旧字段名，然后整块静默不渲染。

### 2.2 DS — 部署战略专家 / 业务方案专家（用户视角主审官）

**不读代码，只当用户。** 模拟真实商户与真实消费者，把业务旅程从头走到底。
DS 的产出不是“测过了”，而是**能指出第几步、在什么输入下、业务说不通**。

专门负责捕获两类缺陷：

1. **死交互与假按钮** —— 排版看起来完全像按钮（有边框、有 hover、有字号对比），
   点下去没有任何反应。这类缺陷所有技术测试都会放过：DOM 存在、无异常、无 4xx。
   只有“以用户身份真点一次并检查世界是否改变”能抓到。
2. **业务语义隔离违规** —— 结构上能跑通、语义上荒谬。典型例子：民宿套房类目下混入
   快递电商商品、金额单位串了、审批流走通但角色根本无权审批。
   判定方法：**读一遍界面上出现的每个名词，问它属不属于当前场景。**

DS 的必查动作：
- 端到端走完整旅程，中途不做任何“这里跳过”的心智补偿；
- 对每一步问“如果我是一个不懂技术的业务员，我会不会在这里卡住”；
- 检查临界场景：0 条、1 条、海量条、超长名称、特殊字符、重复提交；
- 检查技术不报错但业务走不通的路径（流程能提交，但下游无人能处理）。

### 2.3 Core SWE — 平台核心研发工程师（架构与门禁守护者）

**目标：让错误在编译期就无法提交。** 不靠 code review 靠人力记住规则，靠工具让违规写不出来。

必须做到：

1. **增量 typecheck 0 报错拦截** —— 未声明变量（如 `showBanner`）、枚举取值写错、
   可选字段当必填用，全部挡在提交之前。宽松类型（把枚举降级成 `string`）等于拆掉门禁。
2. **模块边界扫描** —— 依赖方向不可逆。核心层不得依赖宿主；工具层不得依赖界面层；
   跨包引用必须走声明的入口。边界一旦靠“约定”维持，就会在赶工时被打破。
3. **统一 API 契约保护** —— 一份契约声明所有接口，界面、工具、worker 分发全部从它派生。
   禁止三处手写同一份清单（必然漂移）；禁止声明了却不暴露（不可达的僵尸接口）。
4. **结构守卫用例** —— 把“某类 bug 曾发生过”固化成断言。例如：所有 SQL 里引用的列名
   必须在真实迁移里存在；契约里的每条路由必须在分发处有实现。

**门禁判据**：typecheck 0 报错、守卫用例全绿。任一红即不得进入下一角色。

### 2.4 PRE / SRE — 产品可靠性工程师

**目标：确保“测过的东西”就是“要上的东西”。**

必须做到：

1. **环境版本指纹握手（Environment Provenance Handshake）** —— 被测环境必须主动报告
   自己跑的是哪个制品指纹（构建号 / 镜像摘要 / 依赖锁哈希），并与本地期望值比对。
   指纹不一致时，**整条链的测试证据作废**，不是打警告。
   这一条专治最经典的翻车：「本地 master 改了，但测试服务器还在跑旧镜像」，
   于是所有验证都是对旧版本的验证，而所有人都以为验过了。
2. **不可变制品** —— 构建产物带指纹、只读、不就地修改。改代码必须重新构建，
   不允许“临时改一下服务器上的文件”这种无法回溯的修补。
3. **发布后健康拨测** —— 上线后主动打健康检查与关键路径探针，确认新版本真的在服务；
   而不是等用户来报错。拨测失败要能一键回滚。
4. **资源回收** —— 测试与验证过程占用的端口、进程、临时实例，退出时必须清理。
   留下脏进程会污染下一次验证，让后面所有人拿到不可信结论。

**PRE 的否决权**：指纹不一致、制品非不可变、拨测未过 —— 任一成立即阻断发布，
不需要论证业务影响。

### 2.5 FDA — 前线架构师

**在任何人写第一行代码之前，把不可逾越的边界画出来。**

必须做到：

1. **组织与租户数据隔离** —— 每个实体归属哪个租户、隔离在哪一层（路由 / 服务 / 数据库）、
   跨租户访问如何被拒。隔离必须在**服务端**强制，客户端传来的租户标识永远不可信。
2. **领域模型边界** —— 哪些概念属于哪个域，什么不允许混在一起。领域边界一旦模糊，
   后续所有功能都会长出跨域的特例分支。
3. **RBAC 权限边界** —— 谁能读、谁能写、谁能批。特别地：**能提案 ≠ 能批准**，
   自批自审的流程等于没有流程。
4. **不可篡改事务边界与守恒** —— 资金、库存、配额类操作必须有原子事务边界与守恒断言
   （进出双向对账、防重复冲销）。守恒破坏通常是静默的，所以必须主动断言而不是事后抽查。

**FDA 的约束是设计约束，不是建议**：隔离、权限、守恒任一条被绕过，交付物整体不予验收。

## 3. 交接门禁（Gate）

按顺序交付，每一道门禁要求的是**证据**，不是自述：

| 门禁 | 移交 | 必须成立 |
|---|---|---|
| G1 设计 | FDA → Core SWE / FDSE | 租户隔离点、领域边界、权限矩阵、守恒断言已写明，且能指出在哪个文件/哪一层强制 |
| G2 可编译 | Core SWE → FDSE | `pnpm -r typecheck` 0 报错；静态守卫用例全绿；契约与实现一致 |
| G3 自测 | FDSE → DS | 状态机分支有覆盖证据；无死穴按钮；无未捕获异常；真实例证据（非仅单测） |
| G4 业务 | DS → 交付 | 端到端业务旅程走通；语义隔离无违规；临界场景无阻塞 |
| G5 环境 | PRE → 交付 | 环境指纹一致；制品不可变；发布后拨测通过；资源已回收 |

**G5 是一票否决且最后执行**：G1–G4 全部成立但指纹不一致时，结论是
「全部重验」，不是「大概没问题」。

## 4. 每类角色对应的失败（为什么不能省）

| 角色 | 只有它能看见的失败 | 省掉后的表现 |
|---|---|---|
| FDA | 跨租户越权、领域混装、权限越界、资金/库存不守恒 | 功能全对，安全与合规全错 |
| Core SWE | 未声明变量、枚举漂移、依赖倒挂、契约与实现漂移 | 赶工时正确性靠记忆维持，改成片重复错误 |
| PRE | 测的不是要上的那一版 | 「已验证」基于旧制品，上线即翻车 |
| FDSE | 非默认分支、死穴按钮、未捕获异常 | 主流程通，真实使用第一步就卡住 |
| DS | 假按钮、业务语义荒谬、技术通但业务不通 | 系统无异常、无报错，用户办不成事 |

**用法**：拿到一个需求，先确认五个角色视角都有交代；评审一个 PR，按本表逐行问
“这条视角谁看过、证据在哪”；上线前，重点确认 G3/G4/G5 是**独立证据**而不是同一批单测的复述。

## 5. 反模式（发现即阻断）

1. **角色自证** —— 开发者自己宣布“业务可用”。业务可用必须由 DS 视角独立走一遍。
2. **证据借用** —— 用单测绿替代真实例验证，用真实例验证替代真浏览器旅程。
   每一层能覆盖的失败类型不同（见第 4 节）。
3. **警告当通过** —— 指纹不一致、守卫红一条、拨测超时，但“先上，回头修”。
4. **只测默认态** —— 默认 Tab / 默认筛选 / 默认空库，一切非默认分支无证据。
5. **假按钮与被吞掉的异常** —— 让界面上不存在没有行为的动作；让每个失败都有明确去向。
6. **宽松类型** —— 为了让编译通过把枚举降级成字符串、把必填改成可选。
   这等于把门禁拆掉换取一次绿灯。
7. **契约多处手写** —— 同一份接口清单在多个文件各写一遍，然后在某次改动中静默漂移。
