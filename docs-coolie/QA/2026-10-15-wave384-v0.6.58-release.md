## 3. 偏差与处置 (诚实登记)

1. **未手工 pre-bump version (调度令 step 3 vs 脚本契约)**
   调度令要求先手工改 app.json/package.json/build.gradle/version.json 再跑脚本; 但
   `release-app.sh [1/9]` 有硬门禁 `当前已是 v$VERSION 即拒绝发版` + `工作树须干净`。
   若先手工提交 bump, 脚本会直接 die。故按脚本真实契约执行: **bump 全权交给脚本** (结果与
   step 3 要求的 4 处版本源完全一致)。version.json 的本地 tracked 副本历史上即非脚本托管
   (停在 0.6.27), 远端 version.json 才是升级检测真值, 已置 0.6.58。

2. **`release-app.sh` 在 `[10/11]` web 段健康验证中断 (exit 1)**
   报错 `❌ web 段健康验证失败: GET / 返回 HTTP 000000`。000000 = curl 连接层失败, 非 HTTP
   错误响应 —— 与仓库已知的「本机代理干扰外网/远端连通」现象一致, 属瞬时抖动。
   复核: 中断后 `GET https://xrobinai.cn/` 实返 `200`, `api/health` commit 已是 `e59cc9bd2`,
   即 **web 段实际部署已成功**, 仅脚本内那一次 curl 探测失败。
   处置: 未重跑整个发版 (重跑会因版本已是 0.6.58 被脚本拒绝且会重复部署); 改为手工补跑
   脚本本应在 `[11/11]/[12/12]` 执行的两件事 —— 4 护栏 (全绿) + tag。APK/COS/version.json/
   OTA/server 均在中断前已完成, 无二次上传风险。
