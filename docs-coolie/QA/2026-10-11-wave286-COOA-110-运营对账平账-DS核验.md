## 四、 DS 业务旅程走查与发现 (F1–F8)

**旅程**: 三方采集 (A `hk_orders` 业务流水 / B `pay_orders`+`pay_refunds` 支付网关 / C 微信支付对账单) → Matcher 比对 → 平账归档 / 差错池 (长款·短款·金额不符·状态不一致) → 复式记账守恒断言 → 台账 (`pay_reconciliations`) + 报告落盘 → 日终平账 → 放行提现。

以「运营/财务操作员」视角逐步走，发现：

| 编号 | 等级 | 发现 | 业务后果 | 建议 |
|---|---|---|---|---|
| **F1** | P1 | **空账期 (0 单日) 口径未定义**：§4.2「全量扫描」默认有流水，未定义当日 0 笔/0 差异是否落日结 (`diff_count=0, status=balanced`) | 无交易日无日结 → INV-5「无对账不放款」**把无交易日提现永久卡死**（业务死路候选，DS 典型） | 明确「0 流水亦须落空日结并平账」或对无流水日显式豁免 |
| **F2** | P1 | **差额调账缺 maker-checker 互斥**：§六 `ops:recon:adjust` 仅要求留审计依据，未强制「申请人 ≠ 审批人」，与租户侧 §2.2 及 INV-6 口径不一致 | 单人可自调自平，内控失效 | 资金调账强制双人复核，与 INV-6 对齐 |
| **F3** | P1 | **长款处置无终态 owner/SLA**：处置=「冻结结算+告警+人工介入」，无 SLA / 责任人 / 超时兜底 / 「核验不通过」终态 | 用户卡在「冻结但不知何时解冻」，流程能发起但下游无人能收尾 | 定义 owner + 超时兜底 + 终态 (退单/冲正/解冻) |
| **F4** | P2 | **短款自动补单缺幂等/去重锚**：「外部对账单取交易号→补发入账事件」，若原支付回调随后到达存在**双入账**风险 | 破坏 INV-4 账实守恒 | 以外部交易号做幂等键 + 冲正策略 |
| **F5** | P2 | **跨日/部分退款 `recon_date` 归属未定义**：状态不一致 (退款) 在日终处理，但跨日退款归属「下单日 or 退款日」未定 | 跨日重复计入 / 漏计 | 明确 recon_date 归属规则 |
| **F6** | P2 | **报告「校验指纹」算法未定义**：§4.4 要求含生成人/时间戳/校验指纹，但算法/字段/payload 未指定，脚手架模板也未输出 | 「不可伪造」在实现上不可验证 | 定义指纹 (如 sha256(payload+caption)) 并在模板中落地 |
| **F7** | P2 | **上游契约断链**：SOP 头注引用 `docs/02_requirements/software-requirements.md`，但仓库根 `docs/` **无 `02_requirements/`**（仅 03/07/08/09） | 违反「No Artifact, No Done」；引用不存在的文件 | 补齐上游或修正引用 |
| **F8** | P3 | **跨项目骨架不一致**：`sys-chanrong-agent/docs/09_operations/` 缺 `02_financial_reconciliation/`（另两交付项目与 root 均有），但其 stub 声明「日终对账平账与资产守恒」 | 声明与骨架不一致 | 统一骨架（该槽位为 cmmi-asset 按需生成，非 hatch 默认，可接受但需注明口径） |

**对账一致项 (正向)**：

- 租户侧审批互斥 (§2.2「审批人 ≠ 申请人」) 明确。
