## 3. 偏差与处置 (诚实登记)

1. **未手工 pre-bump version (调度令 step 1 vs 脚本契约)**
   调度令要求先手工改 app.json/package.json/build.gradle/version.json 再跑脚本; 但
   `release-app.sh [1/9]` 有硬门禁「当前已是 v$VERSION 即拒绝发版」+「工作树须干净」。
   若先手工提交 bump, 脚本会直接 die。故按脚本真实契约执行: **bump 全权交给脚本** (结果与
   step 1 要求的版本源完全一致: app.json 0.6.59/659, package.json 0.6.59, build.gradle
   0.6.59/659)。本地 tracked `version.json` 历史上即非脚本托管 (停在 0.6.27), 远端
   version.json 才是升级检测真值, 已置 0.6.59 —— 保持先例未改本地副本。

2. **`release-app.sh` 在 `[10/11]` web 段健康验证中断 (exit 1)**
   报错 `❌ web 段健康验证失败: GET / 返回 HTTP 000000`。000000 = curl 连接层失败, 非 HTTP
   错误响应 —— 与仓库已知的「本机代理干扰远端连通」现象一致, 属瞬时抖动。
   复核: 中断后 `GET https://xrobinai.cn/` 连续 3 次均 `200`, `api/health` commit 已是
   `94c76813c`, 即 **web 段实际部署已成功**, 仅脚本内那一次 curl 探测失败。处置: 未重跑整个
   发版 (重跑会因版本已是 0.6.59 被脚本拒绝且会重复部署), 改为手工补跑脚本本应在
   `[11/11]/[12/12]` 执行的两件事 —— 4 护栏 (全绿) + tag。APK/COS/version.json/OTA/server
   均在中断前已完成, 无二次上传风险。

3. **发版前工作树含未提交的 wave386 修复 (必须先落库)**
   `publish-ota.sh` / `release-app.sh` 的 EXPO_PUBLIC dev 地址隔离 (wave386) + `execute.ts`
   E2BIG 修复原为未提交状态; `release-app.sh [1/9]` 要求 tracked 树干净, 故分别落库
   `4dee7187f` / `42d191952` 后发版。其中 `execute.ts` 的 wave 归属不在本调度令内, 按原样
   落库以便回溯。

4. **并发写者 (同 wave 的 墨斗/FDA) 对同一脚本追加 wave402 加固 + 重发 OTA**
   工作树在本次发版后 (约 09:04–09:05) 出现第三方改动: `clients/expo/src/instanceTarget.ts`
   (非 dev 构建回环地址硬熔断)、`scripts/release-app.sh` / `clients/expo/scripts/publish-ota.sh`
   (隔离 `.env.local` + 机检 bundle 含生产域名), 标注 `wave402`; 且 **生产 OTA 被重发** ——
   现网 manifest id `20df8f4d-6c9a-412f-9c2c-1a1378d2e83b`, launchAsset
   `index-1e2b8d2144a18c8ae09e20e0ce254459.hbc` (5,677,615 B), runtimeVersion 仍 `0.6.59`
   (与本次 APK 原生运行时一致, 兼容)。对应调度 `.coolie-local/dispatch/20261016T010003Z-wave386-modou-fda.md`。
   处置: 这些文件属同伴在制品, **不在本次发版范围, 未提交、未触碰**; 现网 version.json 仍指向
   本次 release commit `94c76813c`, runtimeVersion 未漂移。`evidence/wave387/ota-manifest.json`
   为**核验时刻的现网快照** (已反映同伴重发后的 manifest)。
