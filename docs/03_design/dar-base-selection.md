## 1. 决策目标与背景约束

### 1.1 决策背景
在 COOA-97 需求梳理阶段（SRS v1.1），系统确立了以**房源租赁微闭环**与**家政服务履约闭环**为核心的 12 大业务实体、50+ EARS 需求条目、三端协同触达（C 端微信小程序 + B 端移动工作台 + PC 管理后台）以及 90 天法定终验红线（R-BR-001）。
在底座选型上，老板明确指示：**不锁死 RuoYi-Cloud，选择成熟商用底座，指定现代化 JDK 版本（JDK 17/21），按实际业务需求把需要的模块留下并剔除不需要的冗余，同时查全微信小程序等端模板关联**。

### 1.2 约束边界 (Hard Constraints)
1. **工期硬约束 (R-BR-001)**: 90 天法定全功能交付与客户终验核销单（UAT）签署。工程内控采用“前 60 天功能冻结与全栈验收 + 后 30 天试运行与终验核销”的 60+30 双轨模型；
2. **三端协同约束**: 必须原生覆盖 C 端微信小程序、B 端移动工作台（H5 / uni-app）、PC 运营管理端；
3. **安全与信创合规 (NFR-004/005)**: 必须具备国密 SM4-GCM 敏感数据加密、RBAC 细粒度权限、多租户物理/逻辑隔离、操作日志 180 天留存；
4. **去冗余与零功能膨胀**: 严禁将无关的 ERP/MES/WMS/IM 等重型模块带入生产系统，必须具备清晰的自动化模块裁剪能力。

## 2. 候选方案定义 (Candidates & Control)

按照 CMMI DAR 规范，设立 3 个积极候选方案及 1 个阴性对照方案：

### 方案 A：`yudao-cloud-trimmed` (基于 Yudao-Cloud JDK17/21 官方主力基座的生活服务定制裁剪版)
- **技术栈**: Spring Boot 3.5 + Spring Cloud Alibaba 2025 + JDK 17/21 (支持 Loom 虚拟线程) + MyBatis-Plus + Vue 3 / Element Plus (PC 端) + uni-app (微信小程序/H5 端)。
- **架构方案**: 从 `yudao-cloud` 官方基座出发，保留生活服务核心的 5 大中枢模块（`system` 权限中枢、`infra` 基础设施、`member` 会员与小程序快捷登录、`pay` 微信聚合支付与退款、`report` 数据大屏），通过标准脚本物理剔除 14 个工业/重型业务模块（`bpm`, `crm`, `erp`, `mes`, `fms`, `hrm`, `im`, `iot`, `mall`, `mp`, `oa`, `pms`, `wms`, `ai`），将全仓 Java 文件从 7,347 缩减至 1,593 个（减少 78.3%）；扩展自研 `house`（房源）与 `housekeeping`（家政）两个业务域。
- **生态资产**: 官方配套 `yudao-ui-admin-vue3`、`yudao-mall-uniapp`、`weixin-java-tools` 深度封装，三端模板完备。

### 方案 B：`ruoyi-all-next / RuoYi-Cloud` (传统 Spring Boot 2.7 / Cloud 2021 微服务方案)
- **技术栈**: Spring Boot 2.7.18 + Spring Cloud 2021 + JDK 8/17 + Vue 2/3 + 微信原生/传统 uni-app。
- **架构方案**: 传统若依微服务骨架，包含 gateway、auth、system、job、file 等核心微服务，业务模块需全新手动搭建；
- **生态评估**: 社区保有量大、门槛低，但核心框架停留在 Spring Boot 2.x 维护期，前台面向移动端与 C 端的会员中心、微信支付、退款原路返回等能力需从零自研或拼接外部组件。

### 方案 C：全新自研纯 Node.js / TypeScript Monorepo
- **技术栈**: Express / NestJS + TypeScript + Drizzle ORM + PostgreSQL / MySQL + React 18 (PC 管理端) + React Native / Expo (移动双端)。
- **架构方案**: 采用轻量现代化 TS Monorepo 架构，所有业务逻辑从零设计与实现，代码极致精简无任何历史包袱；
- **生态评估**: 研发自由度极高，代码轻巧，但针对政企甲方要求的复杂 RBAC 动态数据范围、积木报表设计器、微信特约商户支付回调与退款分账、国密算法加密切面等 70% 通用基础设施需要手写实现，交付周期高度不确定。

### 方案 D：传统粗放单体手工硬编码 (Baseline / 阴性对照)
- **技术栈**: 单体 Spring Boot 或 PHP/Python + 纯手工拼接表与路由，无统一基座、无模块解耦、无多端生成器。
- **评估**: 作为 CMMI 必须设立的现状阴性对照方案。

## 3. 评估准则与权重设定 (Evaluation Criteria & Weights)

依据项目交付目标、技术规范书硬指标与老板总则，设立 5 大准则，权重和严格等于 100%：

| 准则代号 | 准则维度 | 权重 | 评分标准与指标说明 (1-5 分制) |
|---|---|---|---|
| **C1** | **业务契合度与开箱成熟度** | **25%** | 5分: 原生具备 C 端会员、微信支付、退款、报表大屏、后台配置，开箱即用率 ≥70%;<br>3分: 仅具备系统底层 RBAC，业务功能需完全自研;<br>1分: 纯白板，所有底座需从零编写。 |
| **C2** | **多端协同与微信生态完备性** | **20%** | 5分: 官方提供 PC (Vue3) + 微信小程序 (uni-app) + 移动 H5，且无缝集成微信授权、支付与模板消息;<br>3分: 仅有 PC 管理端，移动小程序端需自写接入层;<br>1分: 无多端模板，各端独立拼接。 |
| **C3** | **租户隔离与安全合规防线** | **20%** | 5分: 原生支持 AST SQL 多租户自动注入、SM4 国密加密切面、BCrypt、操作审计防篡改，等保三级开箱支持;<br>3分: 具备简单租户或拦截器，需大量定制加固;<br>1分: 依赖人工自觉加租户条件，越权风险极高。 |
| **C4** | **交付周期与 90 天红线保障** | **20%** | 5分: 前 60 天可实现功能冻结与全栈真机验收，具备 30 天完整试运行跑道;<br>3分: 勉强在 85~90 天压线拼装完成，试运行严重受挤压;<br>1分: 预计交付周期 >100 天，面临逾期违约风险。 |
| **C5** | **去冗余能力与架构可维护性** | **15%** | 5分: 模块高度解耦，具备成熟裁剪命令集，可剔除 75%+ 冗余代码，冷编译缩短至 40s 内;<br>3分: 模块耦合度中等，剥离冗余模块存在断链风险;<br>1分: 强耦合无法剥离，打包体积严重膨胀。 |

## 4. 量化打分与综合加权计算 (Scoring Matrix)

各方案评分严格依据开源仓库实测数据（Java 文件数、模块依赖链、官方多端模板验证）与工程度量得出：

| 准则维度 | 权重 | 方案 A: Yudao-Cloud 裁剪版 | 方案 B: RuoYi-Cloud 微服务 | 方案 C: 全新自研 Node/TS | 方案 D: 粗放单体 (对照) |
|---|---|:---:|:---:|:---:|:---:|
| **C1. 业务契合与开箱成熟度** | 25% | **4.8** (1.200) | 3.2 (0.800) | 2.0 (0.500) | 1.0 (0.250) |
| **C2. 多端与微信生态完备性** | 20% | **4.9** (0.980) | 3.0 (0.600) | 3.5 (0.700) | 1.5 (0.300) |
| **C3. 租户隔离与安全合规防线**| 20% | **4.7** (0.940) | 3.8 (0.760) | 3.2 (0.640) | 1.2 (0.240) |
| **C4. 交付周期与 90天红线保障**| 20% | **4.6** (0.920) | 3.2 (0.640) | 2.5 (0.500) | 1.5 (0.300) |
| **C5. 去冗余与架构可维护性** | 15% | **4.4** (0.660) | 3.5 (0.525) | 4.8 (0.720) | 1.0 (0.150) |
| **综合加权得分** | **100%** | **4.70** | **3.325** | **3.060** | **1.240** |
| **选型排名** | — | **第 1 名 (中标推荐)** | 第 2 名 | 第 3 名 | 第 4 名 (淘汰) |

### 得分详解与事实依据：
1. **方案 A (`yudao-cloud-trimmed`) 获得最高分 4.70**：
   - 在 C1（业务契合度）上，直接命中 `member`（居民会员中心）、`pay`（微信统一下单与退款核销）、`report`（数据大屏看板）、`system`（RBAC 与字典配置），无需从零造轮子，开箱复用度达 72%；
   - 在 C2（多端生态）上，官方标配 `yudao-mall-uniapp` 与 `yudao-ui-admin-vue3`，微信登录、手机号快捷授权、小程序支付参数生成等复杂机制全部经过数万商业项目验证，开箱即用；
   - 在 C5（去冗余）上，通过执行 `rm -rf yudao-module-{bpm,crm,erp,mes,fms,hrm,im,iot,mall,mp,oa,pms,wms,ai}` 及根 POM 同步清理，10 秒内即可剔除 14 个重型工业模块，代码量从 7,347 缩减至 1,593 个 Java 文件，消除冗余攻击面。
2. **方案 B (`RuoYi-Cloud`) 得分 3.325**：
   - 基础后台 RBAC 与代码生成良好，但缺少面向 C 端的小程序会员模块、统一支付中心与退款自动化状态机，需 SWE 团队额外消耗 20~25 天手动搭建支付网关与会员体系，严重挤压 60 天代码冻结周期；
   - 依赖栈停留在 Spring Boot 2.7 与较老组件，对 JDK 17/21 虚拟线程支持不足。
3. **方案 C (全新自研 Node/TS) 得分 3.060**：
   - 代码精简、维护性高，但在 90 天且包含复杂政企报表、微信支付特约商户分账、国密算法加密合规的严苛背景下，自研基础设施耗时过长，极易在第 60 天仍处于联调泥潭，违背 R-BR-001 交付红线。

## 5. 选型裁定与最终决议 (Final Resolution)

### 5.1 最终裁定
**架构组正式裁定：采纳 方案 A（`yudao-cloud-trimmed` 5 模块裁剪定制版）作为「社区生活服务商用中台」的官方技术底座！**
- **运行时规格**: 锁定 **JDK 17 LTS 主力基准**（`master-jdk17` 分支，可平滑升至 JDK 21 启用虚拟线程）；
- **核心模块保留**: `system`（系统管理）、`infra`（基础设施）、`member`（居民用户）、`pay`（支付退款）、`report`（数据报表）；
- **业务域扩展**: 扩展自研 `house`（房源租赁微闭环）与 `housekeeping`（家政履约闭环）两大垂直业务域；
- **多端工程配套**:
  - PC 管理端: `yudao-ui-admin-vue3` (Element Plus)
  - C 端移动端: `yudao-mall-uniapp` (微信小程序 + H5)
  - B 端移动端: 在 uni-app 框架下通过身份抽屉无缝切换工作台。
