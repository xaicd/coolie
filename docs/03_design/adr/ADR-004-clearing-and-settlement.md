# ADR-004: 支付清分、退款准备金与日终结算分账双向平衡守恒架构

- **状态**: 已接受 (Accepted)
- **决策者**: 墨斗 (前线架构师 FDA · modou-fda)
- **日期**: 2026-10-16
- **关联工单**: COOA-92 中台总体架构与技术设计方案
- **关联门禁**: G2 架构与资金事务守恒门禁 (`gate_g2_arch`)
- **上游契约**: COOA-91 SRS v1.0 冻结版 (§5 支付与结算)

---

## 1. 上下文与问题陈述 (Context)
社区生活服务商用中台连接多租户物业、多层级商户（Lv1-Lv5）与广大社区居民。在支付与结算链路中，存在多重资金清分挑战：
1. 涉及平台抽佣（4%~8%）、商户实收、物业分成以及退款准备金（GMV 0.5%）的切分；
2. 存在商户退款、争议仲裁扣款、平台补贴冲抵等多维度动账；
3. 商户结算账期不一（Lv1 T+15 至 Lv5 T+1），需保障 48 小时异议期与可溯源审计。

## 2. 决策驱动力 (Decision Drivers)
1. **资金守恒公理 (Financial Conservation Axiom)**: 任何订单交易，资金进出双向必须 100% 平账，严禁出现单边账或资金溢出；
2. **合规资金存管**: 平台不沉淀用户资金，走微信商户平台服务商分账专户；
3. **退款准备金蓄水池**: 按照 GMV 0.5% 自动计提准备金，避免商户撤场导致用户退款无门。

## 3. 考虑的备选方案 (Considered Options)
1. **方案 A: 实时分账模型**：用户支付后立即触发分账指令至微信。
   - *缺陷*：服务尚未履约（如家政尚未上门），若用户中途退款需走反向分账回退，流程极度繁琐且微信分账撤回有时间窗口限制。
2. **方案 B: 履约完成冻结 + 账期日终结算批处理模型 (T+N)**：
   - 用户支付资金落入平台待清分户；
   - 履约签收后触发清分计算入账待结算池；
   - 每日凌晨 02:00 根据商户等级对应账期（T+7/T+3/T+1）自动生成日终结算单；
   - 赋予商户 48 小时异议缓冲期，无异议后自动调用微信批量分账打款。
3. **方案 C: 线下人工月结对账打款**。

## 4. 决策结果 (Decision Outcome)
**选择 方案 B**。
- **清分公式**: `商户实收 = 订单实付 × (1 - 抽佣率) - 平台补贴商户承担部分`；
- **准备金机制**: `退款准备金 = 订单实付 × 0.005`，自动转入专项子台账；
- **强数学断言**: 结算单生成与分账指令执行前，强制执行：
  ```java
  BigDecimal totalSplit = merchantPayable.add(platformCommission).add(propertyShare).add(reserveFund);
  Assert.isTrue(totalSplit.compareTo(actualPaidAmount) <= 0, "分账金额超出实付资金总额！");
  ```
- **复式记账流水**: 商户资金账户每次动账均写入 `cls_merchant_fund_log`，记录 `before_balance`, `amount`, `after_balance`, `biz_type`, `trace_id`。

## 5. 预期结果与影响 (Consequences)
- **正面收益**:
  - 彻底规避服务未完成即分账的资金坏账风险；
  - 48h 异议期有效阻断客诉争议资金提前出逃；
  - 满足央行支付合规与等保 2.0 三级财务审计要求。
- **负面风险与缓释**:
  - 商户账期等待（T+7 等）可能有现金流顾虑 -> 通过 Lv1-Lv5 履约评级动态激励机制，单量提升与投诉降低后自动缩减账期至 T+3 / T+1。
