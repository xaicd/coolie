## 1. 2026-10-15 今日关键原话与拍板决策 (Customer Utterances Ledger)

### 决策点 1：生产环境工坊会话错误根因清零与高频指标 100% 数据库直驱
- **掌柜原话**:
  - *"工坊 生产环境 工坊会话 还有很多错误,你看看 如何 解决"*
- **历史真实上下文与生产报错复现溯源**:
  1. **现象复现 (issue `775c5dc3-af0e-42b8-96b6-9cf8aa86451b`)**:
     - 掌柜在工坊中提问：
       - `当前项目任务总数，任务完成率`
       - `产物啊`
       - `当前coolie prod的mcp配置全面了吗`
     - 助理出现“空转与反复道歉嘴炮死循环”：
       - *"我两次想拉 API 都返回空，连环境变量探测都是空的... 我不知道当前项目的任务总数真值是几条..."*
       - *"又一次没真发出去 —— 我前面写的是嘴炮，没有真正跑 curl 命令。我每次回复想发工具调用，结果都显示'空反馈'被我自己吞了，然后下一轮我就口头承诺会去做，形成死循环。"*
     - 并在 `2026-10-15 09:12:27` 触发 HTTP 429:
       - `Direct Anthropic API returned HTTP 429: 已达到 Token Plan 用量上限 (2056)`
     - 并在整点 (20:00:05, 21:00:05) 触发例行调度崩溃:
       - `routine scheduler tick failed: Default agent required at dispatchRoutineRun (/opt/coolie/server/src/services/routines.ts:1720:13)`
  2. **三大物理真因定位**:
     - **真因 A：原生直接流式通道缺少工具定义与全量统计注入**:
       - `streamViaDirectAnthropic` 走 Anthropic Messages 协议极速直连输出，但为单轮纯文本未挂载 Tools；
       - `resolveLiveFoundryContext` 仅查询了前 10 条 `openIssues` 与项目名，**未回读全量任务总数、各状态分布、完成率、真实工件清单**；
       - 导致大模型在面对进度大盘问答时，试图“调用 curl/API”却无通道，产生荒诞的“嘴炮道歉死循环”。
     - **真因 B：高频大盘/产物/MCP查询未纳入 Direct Action 硬拦截**:
       - 派单、叫醒、改派已实现原子落盘直驱，但“当前项目任务总数，任务完成率”、“产物列表”、“MCP配置”仍穿透到底层大模型；
       - 带来 5~6 秒延迟、高 Token 消耗，并在模型配额超限 (429) 时直接造成会话中断。
     - **真因 C：交付主线常驻 Routine 缺少默认 Assignee 导致整点 422 报错**:
       - 项目启动时初始化的 `[交付主线例行巡检]` Routine 的 `assignee_agent_id` 初始为空；
       - 每小时整点触发器调度时，`dispatchRoutineRun` 执行硬门禁 `if (!assigneeAgentId) throw unprocessable("Default agent required")`，抛出 422 污染后台系统日志。

- **拍板结论与落盘物理法典**:
  1. **落地三类高频查询 100% 数据库物理直驱 (Direct Action)**:
     - **任务与大盘统计直驱**: 匹配 `任务总数|完成率|进度|项目状态|工单统计`，直接 `COUNT(*)` 真实 issues，5ms 内输出权威 Markdown 统计卡片（总数、已完成、完成率、在办清单、负责人分布），`isTerminal: true`，0 耗 Token，0 错误率；
     - **交付工件资产直驱**: 匹配 `产物|交付物|工件|work products`，直接读取 `issue_work_products`，输出权威资产列表（类型、标题、交付时间、不可变快照）；
     - **MCP 工具池全景审计直驱**: 匹配 `mcp配置|工具池|7大工具`，直接输出控制面 76 项 + 本体 22 项 + 本地 7 工具池实景审计报告。
  2. **全面强化实时底座注入 (`resolveLiveFoundryContext`)**:
     - 在系统提示词中预注入真实任务总数、完成率、在办工单数量、工件总数，保证任何复杂语义对话下大模型均掌握 100% 数据库事实，根绝幻觉与空探针。
  3. **自愈修复 Routine 调度器 422 异常 (`routines.ts`)**:
     - `dispatchRoutineRun` 在 `assigneeAgentId` 为空时，自适应回退到项目 Lead Agent 或公司就绪员工，并持久化回写，彻底消灭整点 422 报错。
  4. **优化模型 429 限流保护与友好降级**:
     - 当直连模型遇 429 配额用尽时，优雅捕获并输出指引，避免流式假死或脏退出。

### 决策点 2：产物交付视图严格项目物理隔离与虚假 Mock / 跨项目历史数据清零
- **掌柜原话**:
  - *"产物 还是 有 历史数据,不归属 项目 的 deploy/xxxx.apk 等等"*
- **历史真实上下文与溯源**:
  1. **跨Tab上下文断裂**: `App.tsx` 在底栏切换至 `artifacts` Tab 时未传递 `initialProjectId`，导致 `ArtifactsScreen` 的 `selectedProjectId` 初始为 `null`，全量拉取全公司历史交付物；
  2. **过滤条件漏洞泄露历史未分类数据**: `ArtifactsScreen.tsx` 在树形渲染时采用 `!a.project || a.project.id === selectedProjectId`，导致历史早期未绑定项目的工单工件（如 XROA-48 的微服务架构门禁设计图与文档）全量侵入新项目的交付目录树；
  3. **假 Mock 模板代码严重污染真交付**: `ProjectDirectoryTree.tsx` 存在人工写死的模板代码注入机制（若未匹配到源码，强制生成 `server.mjs`, `config.mjs`, `schema.sql` 或各模板项目源码），并在 `deploy/` 下无脑注入写死的 `docker-compose.yml`，严重违背 CMMI 5 “真资产、真真值、No Artifact, No Done” 最高法典；
  4. **后端多维项目归属单点脆弱**: `company-artifacts.ts` 过滤 `issue_work_products` 时仅对比了 `issues.projectId`，而未结合工件本身的 `projectId` 执行 `coalesce` 双重校验。
- **拍板结论与落盘物理法典**:
  1. **前端跨Tab上下文强闭环与自愈感知**: `App.tsx` 严格下发 `initialProjectId={chatInitialProjectId}`；`ArtifactsScreen.tsx` 挂载即同步 `getLastProjectId(company.id)`，若仍为空则自动选中首个进行中项目，杜绝无项目全景垃圾数据直接糊脸；
  2. **绝对项目隔离与历史脏数据硬阻断**: 统一收敛为严格项目匹配 `a.project?.id === selectedProjectId`，禁止 `!a.project` 伪兜底放行，确保 0 历史跨项目工件泄露；
  3. **彻底杀灭假 Mock 模板与伪造制品**:
     - `ProjectDirectoryTree.tsx` 彻底移除硬编码的伪造 `deploy/docker-compose.yml` 与各模板源码；
     - `src/` 与 `deploy/` 目录严格按真实归档资产动态挂载，若当前项目尚未归档对应物理制品，则不伪造展示，真正实现“所见即真资产”；
     - 默认展开真实的 `deliverables`（方案册/3D交互预览）与 `media`（视觉图纸），首屏直达真实交付资产。
  4. **后端查询双重原子保护**: `server/src/services/company-artifacts.ts` 采用 `coalesce(issueWorkProducts.projectId, issues.projectId) = query.projectId` 进行双向锁死。

### 决策点 3：软件交付工厂生命周期职责归位 —— 严禁将业务运行期数据混淆为工程软件资产
- **掌柜原话**:
  - *"residential-plan-service 这个项目 按理说 产物 就是 代码,cmmi文档,spec 文档啊"*
- **历史真实上下文与溯源**:
  1. **生命周期三层职责倒置 (公理一破坏)**:
     - 在前期执行空间方案生成批量任务时，数字员工通过 MCP 工具 `residential_plan_upload_coolie` 累计上报了 222 件针对具体户型的房间生成物（9页方案册 PDF/HTML、WebGL 3D 预览、毫米级拓扑 JSON）；
     - 这些产物属于**第三层：业务落地运行系统 (Delivered Application Runtime Data)**，是软件运行产生的业务数据/样本测试集；
     - 但在控制面工件台账中，项目 `residential-plan-service` 却缺失了**第二层：软件制造工程流水线 (Delivery Foundry Engineering Pipeline)** 的核心软件工程真资产：微服务真实源码仓库、CMMI 01~09 全生命周期过程文档、以及敏捷特性规格包 (Spec-Ops SDD)；
     - 导致掌柜在审视 `residential-plan-service` 项目交付物时，满屏全是生成的户型图方案，而真正作为商业交付核心的“微服务代码、CMMI 文档、Spec 规格”完全不可见。
  2. **物理工程资产实际早已高质量就绪**:
     - 真实仓库位于物理路径 `/host-workspace/wenbin/residential-plan-service`（累计 120+ 提交，`src/server.js` 41KB 核心引擎，`Dockerfile` 生产容器编排，`docs/API.md` 30KB OpenAPI 规范，`docs/diagrams/` Archify 交互架构图，`tools/` 14 项 SpaceX 自动化打假门禁 100% 退出码一致且 0 假绿）；
     - 但该物理工作区未以标准 CMMI 01~09 规范组织，也未作为核心工程制品正式归档入库。
- **拍板结论与落盘物理法典**:
  1. **物理目录与 CMMI 01~09 / Spec-Ops 全面实体化归位**:
     - 在 `residential-plan-service` 物理仓库中正式建立与完善 CMMI 01~09 标准规范目录：
       - `01_management/`: 项目立项书与技术选型 DAR 加权权衡矩阵；
       - `02_requirements/`: IEEE 29148 / EARS 软件需求规格说明书 (SRS) 与双向 RTM；
       - `03_design/`: 系统总体架构说明书 (HLD，挂载 Archify `system-architecture.arch.html` & `.svg`) 与详细设计接口契约 (LLD / OpenAPI 3.0 与多模型网关缓存 `model-gateway-caching.arch.html` & `.svg`)；
       - `04_contracts/`: MCP 协议契约与客户端接口定义；
       - `05_verification/`: 14 项 SpaceX 自动化打假门禁集成测试报告 (VER/VAL)；
       - `06_quality_assurance/`: 物理/功能配置审计报告与 CMMI 5 缺陷因果预防；
       - `07_release/`: 生产环境不可变容器镜像部署 SOP 与秒级回滚预案；
       - `08_sre/`: SLO/SLI 矩阵与健康拨测；
       - `09_operations/`: 多租户运营与网关计费对账平账规约；
       - `docs/specs/`: 空间拓扑求解、WebGL 3D 渲染、9页提案册生成、多模型网关四大敏捷特性全息内聚包 (brief, spec, tasks, evidence)。
  2. **控制面工程资产原子注册与三层隔离展示**:
     - 将 `residential-plan-service` 的微服务源码仓库 (`src/`)、容器编排 (`Dockerfile`)、CMMI 01~09 过程资产、OpenAPI 契约、以及 4 大 Spec 规格包正式注册为首要工程制品；
     - 运行期批量生成的户型方案明确归入“业务交付样本 (Sample Deliverables)”，与核心工程软件资产严格分流，确立商业软件交付工厂最高生态位。

### 决策点 4：商业交付项目底座选型与 Monorepo 规范目录严格并轨
- **掌柜原话**:
  - *"residential-plan-service 是不是 没有用底座, 规范目录 也没有用"*
- **历史真实上下文与溯源**:
  1. **底座选型严重缺位 (违反《两大底座自动选型法典》)**:
     - `residential-plan-service` 早期作为纯空间拓扑与 3D 渲染算法验证脚本立项，直接手搓了极其简陋的 Node.js + Express 单体（仅依赖 `express`, `multer`, `cors` 3 个包）；
     - 未走《工坊两大商业交付底座自动选型法典》的选型漏斗，既未派生 `yudao-quad-terminal`，也未派生 `ruoyi-all-next`；
     - 导致该服务沦为无后台中台、无登录认证、无 RBAC 权限、无多租户行级隔离的“裸奔计算引擎”，无法直接作为成熟商业软件向客户独立交付。
  2. **工程目录架构不合规 (违反公理五)**:
     - 根目录为平铺单包结构，缺少 `pnpm-workspace.yaml`，未拆分 `apps/`（业务中台/微服务）与 `packages/`（空间算法核心 SDK / 契约）；
     - 运行期户型生成方案直接在根目录 `storage/` 下无序堆积（上千个文件），导致业务运行数据与工程代码混部，污染版本库；
     - 历史过程资产严重滞后，直到上一轮才人工回补 CMMI 01~09 文档。
- **拍板结论与落盘物理法典**:
  1. **技术诚实直面偏差**: 坦诚向掌柜承认历史遗留手搓单体的架构缺陷，绝不回避、绝不伪造达标；
  2. **确立标准化整改路线图**:
     - 路线 A（轻量 Monorepo 架构治理）：改造成标准 PNPM Monorepo（`apps/service`, `apps/web`, `packages/spatial-core`, `packages/contracts`），剥离 `storage/` 运行时数据；
     - 路线 B（彻底并轨 `ruoyi-all-next` 底座）：以 `ruoyi-all-next` 全栈底座承载，算法内核模块化嵌入，补齐完整的 React 19 + shadcn 商业中台与多租户权限。
